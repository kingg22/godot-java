# Kotlin as a Godot Script Language (issue #42) — design notes

## Problem

[#42](https://github.com/kingg22/kogot/issues/42) asks for `.kt` files to show up in the editor's "Attach Script" dropdown, like `.gd` does. That requires implementing four Godot GDExtension classes: `ScriptLanguageExtension`, `ScriptExtension`, `ResourceFormatLoader`, `ResourceFormatSaver`.

## Core constraint

Kotlin/Native in kogot is **AOT** — classes are compiled into the extension binary at build time. There is no interpreter and no dynamic compilation of `.kt` source at runtime, unlike GDScript. So a `.kt` file can never be "executed as a script" for real: the "script" is a pointer to a `@Godot` class that was **already compiled and registered in ClassDB** when the extension was built.

Checked for prior art:
- `godot-rust` (gdext) does not implement this in its core — only exposes the raw generated bindings for these classes. Full script-language support is a separate downstream project (`godot-rust-script`).
- `godot-kotlin-jvm-utopia` does implement it, but via JVM reflection (`KtClass`/`KtObject` dynamically instantiated/invoked through JNI) — not applicable to Kotlin/Native, which has no runtime reflection or dynamic class loading. Its `Script`/`ScriptInstance` C++ contract (`jvm_script.h`, `jvm_instance.h`) is still a useful semantic reference (method names, placeholder-instance split), since it mirrors Godot's own `core/object/script_language.h` regardless of packaging.

## Explicitly out of scope for #42

Split out to sibling issues by the maintainer, kept separate here on purpose:
- **[#125](https://github.com/kingg22/kogot/issues/125)** — placeholder/runtime instances for the editor Inspector without running the class. `_placeholder_instance_create` is left as an explicit stub referencing #125, not implemented.
- **[#124](https://github.com/kingg22/kogot/issues/124)** — hot reload (`recreate_instance_func`). `_reload` gets the minimum needed to not break the editor, no real hot-reload logic.

## File → class mapping

Not filename convention — a `.kt` file can declare more than one top-level class. Instead: a compile-time registry generated by the KSP processor, mapping each source file to the single `@Godot` class it declares.
- 1 `@Godot` class in the file → enters the registry, addressable from the editor.
- 0 or 2+ `@Godot` classes in the file → excluded from the registry, silently (not an error — the classes remain usable normally, just not individually selectable as "the" script for that file).

## Implementation phases

1. **KSP script registry** (`processor/`) — group `@Godot` classes by `containingFile`, emit a `ScriptFileRegistry` (source path → class short name) via a new generator function alongside the existing `generateCallbacksFile` pattern in `GodotBindingGenerator.kt`.
2. **Concrete script-language classes** (`kotlin-native/binding/`) — `KotlinScriptLanguage`, `KotlinScript`, `KotlinResourceFormatLoader`/`Saver`, implementing only the methods Godot requires for a functioning language integration; registered in `onInitScene()` (not `onInitEditor()`, since exported games — not just the editor — need to resolve `.tscn` scripts referencing `.kt` files).
3. **Real instance proxy** (`_instance_create`) — a `GDExtensionScriptInstanceInfo`-based proxy (cinterop; the struct is already mechanically available via `godot.def`, unused so far) that redirects property/method dispatch into the tables the KSP processor already generates per class, instead of duplicating that codegen. Conceptually mirrors the `ScriptInstanceBridge`/`StructWrapper` prototype in `jvm-ffm`, ported to cinterop.
4. Manual end-to-end verification in the Godot 4.7.1 editor via `kotlin-native/sample`.

Each phase is implemented and verified (`gradlew assemble`, relevant tests) before moving to the next.
